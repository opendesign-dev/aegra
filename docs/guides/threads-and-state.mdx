Threads are the core persistence unit in Aegra. Each thread represents a conversation with its own state, message history, and checkpoints. Runs execute within threads, and state is automatically persisted after each node execution.

## Creating threads

```python
import asyncio
from langgraph_sdk import get_client


async def main():
    client = get_client(url="http://localhost:2026")

    # Create a thread
    thread = await client.threads.create()

    # Create with metadata
    thread = await client.threads.create(
        metadata={"user_name": "Alice", "session": "onboarding"},
    )

    # Create with a specific ID (idempotent)
    thread = await client.threads.create(
        thread_id="my-thread-123",
        if_exists="do_nothing",  # Don't error if it already exists
    )


asyncio.run(main())
```

## Thread status

Threads have a status that reflects their current state:

| Status | Meaning |
|--------|---------|
| `idle` | No active run, ready for new input |
| `busy` | A run is currently executing |
| `interrupted` | A run paused for human input |
| `error` | The last run ended with an error |

```python
thread = await client.threads.get(thread_id)
print(thread["status"])  # "idle", "busy", "interrupted", "error"
```

<Note>
  The snippets below assume you are inside an `async def` function with an initialized `client` — see the example above.
</Note>

## Getting thread state

The state contains the current values of all state fields, information about what nodes will execute next, and any pending interrupts.

```python
state = await client.threads.get_state(thread_id)

# Current state values (your State schema fields)
print(state["values"])

# Next nodes to execute (empty if completed)
print(state["next"])

# Pending tasks
print(state["tasks"])

# Active interrupts (if thread is interrupted)
print(state["interrupts"])

# Checkpoint info
print(state["checkpoint"]["checkpoint_id"])
```

## Updating thread state

You can modify thread state directly, for example to inject data or correct values:

```python
await client.threads.update_state(
    thread_id,
    values={"messages": [{"type": "human", "content": "Injected message"}]},
    as_node="agent",  # Apply update as if it came from this node
)
```

## Checkpoint history

Every state change creates a checkpoint. You can browse the full history:

```python
# Get recent checkpoints
history = await client.threads.get_history(thread_id)

for entry in history:
    print(f"Checkpoint: {entry['checkpoint']['checkpoint_id']}")
    print(f"  Values: {entry['values']}")
    print(f"  Next: {entry['next']}")
```

### Get state at a specific checkpoint

```python
# Go back in time to a specific checkpoint
state = await client.threads.get_state(
    thread_id,
    checkpoint={"checkpoint_id": "your-checkpoint-id"},
)
```

This is useful for debugging, replaying, or branching conversations from a previous point.

## Searching threads

Find threads by status or metadata:

```python
# Search by metadata
threads = await client.threads.search(
    metadata={"user_name": "Alice"},
)

# Search by status
threads = await client.threads.search(
    status="interrupted",
)

# With pagination
threads = await client.threads.search(
    limit=20,
    offset=0,
)
```

### Filtering by creation time

`created_after` and `created_before` narrow the search to a creation window. Both bounds are inclusive and accept ISO 8601 timestamps; a timestamp without an offset is read as UTC. An inverted window (`created_after` later than `created_before`) is rejected with a 422 rather than silently matching nothing.

The SDK client does not expose these fields yet, so call the endpoint directly:

```python
import httpx

async with httpx.AsyncClient(base_url="http://localhost:2026") as http:
    resp = await http.post(
        "/threads/search",
        json={
            "created_after": "2026-01-01T00:00:00Z",
            "created_before": "2026-02-01T00:00:00Z",
            "sort_by": "created_at",
            "sort_order": "desc",
            "limit": 100,
        },
    )
    threads = resp.json()
```

`POST /threads/count` accepts the same body and returns the matching total. Both endpoints page with `limit` (max 1000) / `offset`.

### Listing conversations for one assistant

A thread's `metadata.assistant_id` records the **last** assistant that ran on it, so it is a useful filter but not a complete history when several assistants share a thread. Combine it with `extract` to get a conversation list with a last-message preview in a single request:

```python
resp = await http.post(
    "/threads/search",
    json={
        "metadata": {"assistant_id": assistant_id},
        "created_after": "2026-01-01T00:00:00Z",
        "sort_by": "created_at",
        "sort_order": "desc",
        "extract": {"last_message": "values.messages[-1].content"},
        "limit": 100,
    },
)
```

For assistant attribution that survives multiple assistants on one thread, query the runs instead — see [Searching runs](#searching-runs) below.

## Searching runs

`POST /runs/search` queries the `runs` table across every thread you own. Unlike thread metadata, each run stores its own `assistant_id` column, so this is the authoritative way to ask "what did this assistant do, and when":

```python
resp = await http.post(
    "/runs/search",
    json={
        "assistant_id": assistant_id,      # a graph id is also accepted
        "status": "success",
        "created_after": "2026-01-01T00:00:00Z",
        "created_before": "2026-02-01T00:00:00Z",
        "sort_by": "created_at",
        "sort_order": "desc",
        "limit": 100,
    },
)
runs = resp.json()

# Then pull each conversation's checkpoint history
for run in runs:
    history = await client.threads.get_history(run["thread_id"])
```

Available filters: `assistant_id`, `thread_id`, `status`, `metadata` (JSONB containment), `created_after`, `created_before`. Results are paginated with `limit` (max 1000) / `offset`, sorted by `sort_by` / `sort_order` (default `created_at` descending), and `select` projects fields.

`POST /runs/count` accepts the same body and returns the matching total. `GET /threads/{id}/runs` takes the same `created_after` / `created_before` window when you already know the thread.

## Listing threads

```python
threads = await client.threads.search()
for thread in threads:
    print(f"{thread['thread_id']}: {thread['status']}")
```

## Deleting threads

Deleting a thread cancels any active runs and removes all state:

```python
await client.threads.delete(thread_id)
```

## Thread metadata

Threads automatically track metadata about their usage:

- `owner`: User identity at creation time (mirrors `user_id` on the Thread object, which is used for access control)
- `assistant_id`: Last assistant used — overwritten on each run, so use [run search](#searching-runs) when a thread spans several assistants
- `graph_id`: Last graph executed

You can add your own metadata at creation or update time:

```python
# Update metadata
await client.threads.update(
    thread_id,
    metadata={"priority": "high"},
)
```

## User isolation

When authentication is enabled, threads are automatically scoped to the authenticated user. Users can only see and interact with their own threads.
