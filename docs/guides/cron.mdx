Aegra supports scheduled runs via a background cron scheduler. Cron jobs are stored in PostgreSQL and fired by a polling loop that runs inside every server instance.

## Prerequisites

Enable the scheduler (it is on by default):

```bash
CRON_ENABLED=true                  # default: true
CRON_POLL_INTERVAL_SECONDS=60      # default: 60
CRON_CLAIM_DURATION_SECONDS=300    # default: 300 (5 min lease)
CRON_MAX_PER_USER=100              # default: 100, 0 disables
CRON_ALLOW_SECONDS_SCHEDULE=false  # default: false
CRON_MISFIRE_GRACE_SECONDS=0       # default: 0 (always catch up)
CRON_MAX_CONSECUTIVE_FAILURES=10   # default: 10, 0 retries forever
```

See the [environment variables reference](/reference/environment-variables#cron-scheduler) for all options.

<Warning>
**Delivery semantics: at-least-once.** When the scheduler claims a cron, the claim is held for `CRON_CLAIM_DURATION_SECONDS`. If a worker crashes between claiming and committing the run advance, another tick re-fires the cron once the claim expires. Make agent runs idempotent if duplicate firings are unacceptable.
</Warning>

<Note>
**Per-user cap.** A single user can own at most `CRON_MAX_PER_USER` crons (default 100). Creating beyond the cap returns HTTP 429. Set `CRON_MAX_PER_USER=0` to disable.
</Note>

<Note>
**Sub-minute schedules.** 6-field (seconds-first) schedules like `*/30 * * * * *` are rejected unless `CRON_ALLOW_SECONDS_SCHEDULE=true`. They multiply scheduler load and DB writes per minute.
</Note>

## Creating a stateless cron

A stateless cron fires against a new thread on every occurrence:

```python
import asyncio
from langgraph_sdk import get_client

async def main():
    client = get_client(url="http://localhost:2026")

    run = await client.crons.create(
        assistant_id="agent",
        schedule="0 9 * * *",   # every day at 09:00 UTC
        input={"messages": [{"role": "user", "content": "Good morning report"}]},
    )
    print(f"Cron ID: {run['cron_id']}")

asyncio.run(main())
```

Aegra accepts the graph ID directly in `assistant_id` for cron creation and resolves it to the default assistant for that graph at request time.

Creating a cron never fires a run. `POST /runs/crons` persists the record and returns the `Cron`; the scheduler owns every firing, starting at the schedule's next occurrence. By default each stateless cron run deletes its ephemeral thread after the run completes.

<Note>
  The snippets below assume you are inside an `async def` function with an initialized `client`.
</Note>

## Thread cleanup for stateless crons

Stateless crons create a fresh thread for every execution. Control what happens to that thread after the run finishes with `on_run_completed`:

- `"delete"` (default) deletes the ephemeral thread automatically after the run completes.
- `"keep"` preserves the thread so you can inspect its state or runs later.

```python
run = await client.crons.create(
        assistant_id="agent",
        schedule="0 9 * * *",
        on_run_completed="keep",
        input={"messages": [{"role": "user", "content": "Daily report"}]},
)

print(run["cron_id"])
```

When you keep stateless cron threads, you are responsible for cleaning them up. For long-lived deployments, use thread TTL policies or a separate cleanup job if you do not want preserved threads to accumulate.

## Creating a thread-bound cron

Bind a cron to a specific thread so every firing continues the same conversation:

```python
thread = await client.threads.create()

run = await client.crons.create_for_thread(
    thread_id=thread["thread_id"],
    assistant_id="agent",
    schedule="0 8 * * 1",   # every Monday at 08:00 UTC
    input={"messages": [{"role": "user", "content": "Weekly digest"}]},
)
print(f"Cron ID: {run['cron_id']}")
```

## Cron expression format

Aegra uses [croniter](https://github.com/kiorky/croniter) for schedule parsing.

### Standard 5-field format

```
┌──── minute (0-59)
│ ┌──── hour (0-23)
│ │ ┌──── day of month (1-31)
│ │ │ ┌──── month (1-12)
│ │ │ │ ┌──── day of week (0-6, Sunday=0)
│ │ │ │ │
* * * * *
```

| Expression | Meaning |
|---|---|
| `0 9 * * *` | Every day at 09:00 |
| `*/15 * * * *` | Every 15 minutes |
| `0 9 * * 1` | Every Monday at 09:00 |
| `0 0 1 * *` | First day of every month at midnight |

### Seconds-level 6-field format

Prefix the standard expression with a seconds field for sub-minute scheduling:

```
*/30 * * * * *   # every 30 seconds
```

## Timezone support

By default schedules use UTC. Pass an [IANA timezone name](https://en.wikipedia.org/wiki/List_of_tz_database_time_zones) to fire in local time:

```python
run = await client.crons.create(
    assistant_id="agent",
    schedule="0 9 * * *",       # 09:00 in New York time
    timezone="America/New_York",
    input={"messages": [{"role": "user", "content": "Morning standup"}]},
)
```

The server stores the timezone alongside the cron record and converts to UTC internally. Passing an invalid timezone name results in an HTTP 422 error.

<Note>
  When updating a cron's schedule without changing its timezone, the existing timezone is preserved automatically.
</Note>

<Warning>
**Daylight saving transitions follow croniter semantics.** A wall-clock schedule inside the hour a zone repeats fires **twice** on the fall-back day (`30 1 * * *` in `America/New_York` matches both 01:30 EDT and 01:30 EST), and one inside the hour a zone skips is pushed to the next valid time on the spring-forward day (`30 2 * * *` fires at 03:00). Use UTC for schedules that must fire exactly once per day regardless of the local calendar.
</Warning>

## Listing and searching

```python
# Search by assistant
crons = await client.crons.search(assistant_id="agent")

# Search by thread
crons = await client.crons.search(thread_id="<thread_id>")

# Count matching crons
total = await client.crons.count(assistant_id="agent")
```

## Updating a cron

```python
updated = await client.crons.update(
    cron_id="<cron_id>",
    schedule="0 10 * * *",  # new schedule
    enabled=False,           # pause without deleting
)
```

Supported update fields: `schedule`, `timezone`, `enabled`, `end_time`, `metadata`, and every run parameter the create accepts — `input`, `config`, `context`, `webhook`, `interrupt_before`, `interrupt_after`, `on_run_completed`, `multitask_strategy`, `stream_mode`, `stream_subgraphs`, `command`, `durability`, `after_seconds`.

Payload fields are merged, not replaced: patching `input` leaves a previously stored `config` in place. `metadata` is a full replace, matching SDK behavior. There is no way to unset a payload field — send a new value instead.

## Disabling and re-enabling

```python
# Pause
await client.crons.update(cron_id="<cron_id>", enabled=False)

# Resume
await client.crons.update(cron_id="<cron_id>", enabled=True)
```

Disabled crons are ignored by the scheduler but remain in the database. You can also create a cron paused by passing `enabled=False` at creation.

Re-enabling recomputes `next_run_date` when the stored one is already in the past, so resuming a long-paused cron does not fire immediately. Any update also resets the failure counter described below.

## Failure handling

A firing that fails is settled in one of two ways, so a broken cron neither hammers the server nor stops silently:

| Cause | This occurrence | Counts toward the cap |
|---|---|---|
| 5xx during run setup (DB, executor) | retried on the next tick | yes |
| 409 — previous occurrence still running | skipped | no |
| 404 / 422 — missing graph, invalid payload | skipped | yes |

After `CRON_MAX_CONSECUTIVE_FAILURES` consecutive failures the scheduler logs a warning and sets `enabled=false`. Any successful firing — or any `PATCH` to the cron — resets the counter.

Separately, `CRON_MISFIRE_GRACE_SECONDS` bounds how late an occurrence may be. The default of `0` always catches up, so a cron due during an outage fires once at restart; set it to skip occurrences that are too stale to be useful.

## Deleting a cron

```python
await client.crons.delete(cron_id="<cron_id>")
```

Deletion is permanent. When a cron is bound to a thread and that thread is deleted, the cron is removed atomically as well (`ON DELETE CASCADE`).

## Limitations

- **Scheduled runs skip per-request auth handlers.** Creating a cron runs the full auth chain (`crons.create` → `assistants.read` → `threads.read`/`search`), but each *scheduled firing* executes as a background daemon under the cron owner's identity and does not re-dispatch `@auth.on(...)` handlers. Put per-run authorization logic in the graph itself if it must apply to scheduled runs.

  Before forging that identity the scheduler calls `aegra_api.services.cron_scheduler.validate_cron_user(user_id)`, which accepts any non-empty id. Replace that module attribute at startup to check your own identity store — returning `False` disables the cron instead of firing it, so a revoked account stops running scheduled work.
- **Cron metadata is not copied onto fired runs.** `metadata` set on a cron is stored on the cron record for search and filtering, but is not propagated to the runs the cron creates.
- **Delivery is at-least-once.** Under a crash between firing and advancing the schedule, a run can fire more than once for a single occurrence. Make scheduled work idempotent.

## Pending approvals

When a thread-bound cron's run pauses on `interrupt()` (or a static breakpoint), the thread goes `interrupted` and the following occurrences are **skipped rather than queued**: firing anyway would append input and advance the checkpoint, discarding the context the approver is looking at. Resume with `command={"resume": [{"type": "accept" | "edit" | "response" | "ignore", "args": ...}]}` — see [Human-in-the-loop](/guides/human-in-the-loop).

A cancelled run also settles as `interrupted`, but cancels carry `cancel_requested` and are excluded from the wait, so stopping a run never trips another run's approval timeout.

After `CRON_APPROVAL_TIMEOUT_SECONDS` (default 24h, `0` waits forever) the scheduler stops waiting, so one unattended approval cannot pause a schedule permanently. What it does then depends on what the pause offers:

- **The interrupt declares `config.allow_ignore`** (the [HumanInterrupt](/guides/human-in-the-loop) convention, as in `examples/react_agent_hitl`): the scheduler answers it with `{"resume": [{"type": "ignore", "args": null}]}` — a rejection, delivered through your graph's own rejection path. That occurrence is spent answering the approval rather than starting a new turn, and the resume carries the cron's stored `config`, `context`, breakpoints, and `webhook`.
- **Anything else** — a plain `interrupt("...")`, a payload without `allow_ignore`, or a static breakpoint: the scheduler will not guess. It releases the thread to `idle` and lets the next occurrence run. The paused runs keep their `interrupted` status, and the checkpoint still holds the pending interrupt, so the next firing re-runs the paused node and asks again.

<Warning>
Auto-rejection is deliberately narrow. A graph that does `value = interrupt("Provide value:")` receives the resume value raw, where an ignore-response list is a crash at best — and reads as approval to any graph that only checks truthiness. Declare `config.allow_ignore` only if your graph handles that response as a rejection.
</Warning>

<Note>
Detecting a rejectable pause reads the materialized `thread_state.interrupts`. With `THREAD_STATE_MATERIALIZE=false` no pause looks rejectable, so every timeout falls back to releasing the thread.
</Note>
