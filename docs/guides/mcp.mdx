---
title: "MCP server"
description: "Expose your graphs as Model Context Protocol tools over Streamable HTTP."
---

Aegra serves a [Model Context Protocol](https://modelcontextprotocol.io) endpoint that exposes **each graph as its own tool**. The tool name is the graph id and its input schema is the graph's own input schema, mirroring the LangGraph Platform MCP surface rather than offering generic `list_assistants` / `run_assistant` tools.

Any MCP client — Claude Code, Claude Desktop, Cursor, or your own — can call your agents as tools.

## Endpoint

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/mcp` | Streamable HTTP transport (JSON-RPC) |
| `GET` | `/mcp` | Server-initiated stream |
| `DELETE` | `/mcp` | Session termination |

<Note>
The endpoint is registered as an exact route, so `/mcp` responds directly with no redirect. This matters because MCP clients build on httpx, which does not follow redirects by default.
</Note>

## Enabling and disabling

MCP is on by default. Turn it off with either switch:

```bash
MCP_ENABLED=false
```

```json aegra.json
{
  "http": {
    "disable_mcp": true
  }
}
```

Either one suppresses the mount entirely — the routes do not exist, rather than returning 403.

## Connecting a client

Point any MCP client at the Streamable HTTP endpoint:

```json
{
  "mcpServers": {
    "aegra": {
      "type": "http",
      "url": "http://localhost:2026/mcp",
      "headers": {
        "Authorization": "Bearer <token>"
      }
    }
  }
}
```

The `Authorization` header is only needed when your deployment has auth configured. See [Authentication](/guides/authentication).

## How graphs map to tools

For a deployment with `graphs: {"agent": ..., "researcher": ...}` in `aegra.json`, `tools/list` returns:

| Tool name | Description | Input schema |
|---|---|---|
| `agent` | Run the 'agent' agent and return its final state. | The graph's input JSON schema |
| `researcher` | Run the 'researcher' agent and return its final state. | The graph's input JSON schema |

Calling a tool invokes the graph and returns its **final state**, serialized as JSON in a single text content block.

<Note>
**Schema fallback.** MCP requires an object input schema. When a graph's schema cannot be derived, or is not of type `object`, Aegra advertises a permissive `{"type": "object", "additionalProperties": true}` instead. The fallback is never cached, so a transient failure does not stick.
</Note>

<Note>
**Schema cache.** Deriving a graph's input schema recompiles factory graphs, so schemas are cached per graph and invalidated on hot reload.
</Note>

## Authentication and authorization

MCP requests go through the **same auth backend as the REST API**. Auth is enforced by the MCP app itself, because FastAPI's automatic auth application does not descend into a mounted sub-app.

Two things happen on every call:

1. **Authentication** — the caller is resolved via the same `require_auth` path as REST. A failure surfaces as an MCP error with `Unauthorized:` and the detail. A deployment with no auth configured resolves to the anonymous user.
2. **Authorization** — `@auth.on` handlers registered for `threads.create_run` are dispatched **before** the graph runs, exactly as on the REST run path. A denying handler raises before any execution; an allowing handler may inject run `config` and `context`.

Tools therefore always run under the caller's identity, not a service identity.

```python
# This handler applies to MCP tool calls as well as REST runs.
@auth.on(resources="threads", actions="create_run")
async def authorize_run(ctx: Auth.types.AuthContext, value: dict):
    if ctx.user.identity not in ALLOWED:
        raise Auth.exceptions.HTTPException(status_code=403)
```

## Tracing

MCP calls invoke the graph inline rather than going through the run executor, so trace context is bound explicitly. Spans carry `source: "mcp"` in their metadata alongside the usual run, thread, graph, and user identifiers. See [Observability](/guides/observability).

## Limitations

- **Stateless — one fresh thread per call.** Every tool invocation generates a new `thread_id` and invokes the graph once. There is no conversation continuity between calls, and no way to target an existing thread.
- **No streaming.** The tool returns only the final state. Use the [streaming API](/guides/streaming) or the Runs API when you need intermediate tokens or events.
- **No human-in-the-loop.** Because each call runs to completion inline, interrupts cannot be surfaced or resumed over MCP. Use the Runs API for [HITL flows](/guides/human-in-the-loop).
- **Tools are graphs, not assistants.** The tool set comes from the graphs declared in `aegra.json`. Assistant-level `config`, `context`, and versioning are not applied — an assistant id is not a valid tool name.
- **No run record.** MCP invocations do not create rows in the `runs` table, so they are absent from run search, webhooks, and run TTL sweeps.
