---
title: "Retention & TTL"
description: "Keep threads, checkpoints, and run rows from growing without bound."
---

A long-running deployment accumulates three kinds of data: **threads** (with their checkpoints), **run rows**, and **store items**. Each has its own retention mechanism, and they are independent — enabling one does not affect the others.

<Warning>
Every sweeper on this page **deletes permanently**. There is no soft delete, no recycle bin, and no undo. All of them are off by default; enable them deliberately and verify the age thresholds against your compliance and support requirements first.
</Warning>

## What each mechanism covers

| Mechanism | Deletes | Default | Trigger |
|---|---|---|---|
| Thread TTL sweeper | Threads with no active run, plus their checkpoints and runs | Off | Background, every `CHECKPOINTER_SWEEP_INTERVAL_MINUTES` |
| Per-thread `ttl` | Overrides the sweeper's age threshold for one thread | Unset | Same sweeper |
| Run TTL sweeper | Terminal run rows only | Off | Background, hourly |
| `POST /threads/prune` | Named threads, or all but the newest checkpoint | — | On demand |
| Store TTL | Store items | Off | Configured on the store |

## Thread and checkpoint retention

The thread sweeper deletes threads that are older than their TTL **and** have no `pending` or `running` run. The age threshold is the thread's own `ttl` when it has one, falling back to `CHECKPOINTER_TTL_MINUTES`. Deleting the thread row cascades to its runs; checkpoints are deleted through the checkpointer.

```bash
CHECKPOINTER_TTL_ENABLED=true
CHECKPOINTER_TTL_MINUTES=43200        # 30 days
CHECKPOINTER_SWEEP_INTERVAL_MINUTES=60
CHECKPOINTER_SWEEP_BATCH_SIZE=100
```

Each tick claims a batch with `FOR UPDATE SKIP LOCKED` and holds the locks until commit, so concurrent instances sweep disjoint threads rather than fighting over the same rows.

A checkpoint deletion that fails is logged and skipped — the thread row is still removed, so a storage-level error does not stall the sweep.

<Note>
LangGraph's checkpointer has no native TTL. This sweeper is what implements thread and checkpoint retention for Aegra.
</Note>

## Per-thread TTL

Threads accept a `ttl` on create and update, expressed as minutes or as a config dict:

```python
thread = await client.threads.create(ttl=1440)                          # minutes
thread = await client.threads.create(ttl={"ttl": 1440, "strategy": "delete"})
```

Read it back with `include`:

```python
thread = await client.threads.get(thread_id, include=["ttl"])
```

Validation rejects non-positive values, JSON booleans, and any `strategy` other than `"delete"` with a 422.

The thread sweeper honours this value: a thread with its own `ttl` is swept at that age, and threads without one fall back to `CHECKPOINTER_TTL_MINUTES`.

<Note>
A per-thread `ttl` only takes effect while `CHECKPOINTER_TTL_ENABLED=true`. With the sweeper off, the value is stored and returned but nothing deletes.
</Note>

## Run row retention

On a busy thread the `runs` table grows far faster than the thread itself. The run sweeper prunes **terminal run rows only** — `success`, `error`, `interrupted`, and `timeout`. Thread state and checkpoints are untouched, so conversation history survives.

```bash
RUN_TTL_ENABLED=true
RUN_TTL_MINUTES=10080   # 7 days
```

The sweep runs hourly and deletes up to 1000 rows per tick; both are fixed constants. The delete predicate inlines the status literals so it matches the `idx_runs_ttl_sweep` partial index, keeping the scan off the hot `pending`/`running` rows.

<Note>
`webhook_deliveries` rows cascade with their run. Pruning runs therefore discards webhook delivery history, including dead-lettered rows. See [Webhooks](/guides/webhooks).
</Note>

## On-demand pruning

`POST /threads/prune` prunes specific threads without waiting for a sweeper:

```python
# Delete threads entirely (runs, checkpoints, row)
await client.http.post("/threads/prune", json={
    "thread_ids": ["thread_a", "thread_b"],
    "strategy": "delete",
})

# Keep the threads, drop all but the newest checkpoint per namespace
await client.http.post("/threads/prune", json={
    "thread_ids": ["thread_a"],
    "strategy": "keep_latest",
})
```

The response is `{"pruned_count": <n>}`. Threads that are missing or owned by another user are **skipped silently** rather than raising, so the count can be lower than the number of ids you sent.

`keep_latest` is the safer option for shrinking storage: the thread stays usable and only its checkpoint history is collapsed.

## Store retention

Store items have their own TTL, configured on the store rather than by a sweeper, plus per-request `ttl` on put and `refresh_ttl` on get and search. See [Store](/guides/store).

## Deletion cascades

Know what disappears with what before enabling anything:

```
thread
 ├─ runs                      (ON DELETE CASCADE)
 │   └─ webhook_deliveries    (ON DELETE CASCADE)
 ├─ thread_state              (ON DELETE CASCADE)
 ├─ crons bound to the thread (ON DELETE CASCADE)
 └─ checkpoints               (deleted via the checkpointer)
```

Deleting a run removes only that run and its delivery rows.

## Limitations

- **Run TTL is deployment-wide.** Unlike threads, runs have no per-run `ttl` override.
- **Run sweep cadence and batch size are not configurable.** Hourly, 1000 rows per tick. A backlog larger than that drains over successive ticks.
- **Thread TTL keys off `updated_at`, not last read.** A thread nobody has written to is swept even if it is being read regularly.
- **No dry-run mode.** There is no way to preview what a sweeper would delete. Query the equivalent predicate yourself before enabling on production data.
- **Sweepers run in every instance.** They are safe to run concurrently thanks to `SKIP LOCKED`, but they do add background query load per pod.
